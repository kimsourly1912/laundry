# Language: English and Khmer

← [Docs](../README.md) · Visual rules: [ui.md](./ui.md) · Review: [ui-review-checklist.md](./ui-review-checklist.md)

The app speaks **English by default** and Khmer as the second language ([D4](../decisions.md#d4-english-is-the-default-language), replacing spec P12's Khmer default). Every screen works fully in both. This page covers UI strings, Khmer type, money and date display, and shop data stored in two languages.

Status: the i18n module (`@nuxtjs/i18n`) is added in M1.6, after checking its current docs with Nuxt 4 and SPA mode (spec §17). Formatting rules below were checked with Node 24's `Intl`; browser output is checked on a real low-end Android phone in M1.6.

---

## 1. Locales

| Code | Language | Role |
|---|---|---|
| `en` | English | Default. First load, sign-in, the public ticket page without a preference |
| `km` | Khmer | Second language, complete: every key exists in both files |

- **Who chooses:** the user, in the app (account page and the sign-in page). The choice is kept in the browser. A shop's setting `language` (default `en`) decides the language of that shop's **customer-facing** output: Telegram messages and the public ticket page.
- **No locale in the URL** for app pages (they are SPA screens behind sign-in). The public ticket page uses the shop's language, with a switch on the page.
- `<html lang>` follows the active locale.

## 2. Strings

- **No hard-coded UI strings.** Every visible string, `aria-label`, page title, toast, confirm text and validation message is a key in `app/locales/en.json` **and** `app/locales/km.json`. A key missing from one file fails a unit test (M1.6).
- **Server error messages** are written for the user in the language of the request (spec §9: `{ code, message }`). The app may also map `code` to its own key; the `code` never changes with the language. Settled in [D9](../decisions.md#d9-flat-error-body): server messages are English; the app shows its own translated text for each `code` and falls back to the server's message.
- **Telegram messages** are built on the server from the shop's language, with their own keys owned by the notifications feature (M4).

### Key naming

```text
<feature>.<screen or part>.<element>
common.<group>.<element>          shared words: actions, states, errors
```

| Key | Text (en) |
|---|---|
| `orders.list.title` | Orders |
| `orders.detail.markReady` | Mark ready |
| `orders.status.in_progress` | In progress |
| `customers.form.phone.label` | Phone |
| `common.actions.save` | Save changes |
| `common.states.loadError` | Couldn't load this. Try again. |

- Keys are `camelCase` parts joined by dots. Enum values keep their API spelling (`orders.status.in_progress`), so code can build the key from the value.
- **One key per meaning, not per word.** "Ready" as a status and "Mark ready" as an action are two keys.
- **Use placeholders, never concatenation:** `"orders.done.created": "Order #{number} created"`. Word order differs between Khmer and English.
- Plurals use the module's plural syntax. Khmer doesn't change nouns for number; English does.
- Keys live in the file of the locale, grouped by feature. A feature's keys are removed with the feature.

### Writing Khmer copy

- Short, plain words an owner at the counter understands. Prefer the words on today's paper tickets.
- Khmer copy is reviewed by a native speaker before a screen ships to a real shop. Until then, mark new Khmer strings in the PR so they are reviewed.

## 3. Khmer type

- **Font:** a Khmer-capable font is set once in `tailwind.css` (Nuxt UI's `--font-sans`), with the Latin font first and a Khmer font next. Candidate: **Noto Sans Khmer** (wide coverage, open license), self-hosted so the CSP stays `font-src 'self'`. Chosen and checked in M1.6.
- **Line height:** Khmer stacks consonants and vowel signs above and below the line. Use Tailwind's line heights (`leading-relaxed`, about 1.6) for Khmer body text; never a fixed height on a text container; never `leading-none` or `truncate` on Khmer text that can have subscripts (they get cut).
- **Line breaks:** Khmer has no spaces between words. Browsers break lines with dictionary data; long words can still overflow. Use `break-words` on text containers.
- **Size:** Khmer at `text-sm` is harder to read than Latin. If owners find it too small, the fix is a theme change (once, in `tailwind.css`), never per page.
- Check every screen in Khmer at 320px: buttons, tabs and badges are often longer in Khmer.

## 4. Money, numbers and dates

All display goes through **shared formatters** (`app/utils`, M1.6) built on `Intl`. ESLint will forbid hand-made `toLocaleString` / `Intl.DateTimeFormat` calls outside them once they exist.

### Money (spec T12)

- Amounts are integers in **minor units** with a currency code: KHR = riel (no decimals), USD = cents.
- **Always set the fraction digits from the currency.** `Intl` gives KHR two decimals by default (`13,500.00៛`); riel have none. KHR: `maximumFractionDigits: 0`. USD: 2.
- Checked output (Node 24): `km` KHR → `13,500៛`; `km` USD → `12.50$`; `en` USD → `$12.50`; `en` KHR → `KHR 13,500` (a code, not a symbol).
- **Digits:** `km-KH` gives Latin digits by default (`13,500`). Khmer digits (`១៣.៥០០`) exist (`numberingSystem: 'khmr'`), but paper tickets and phone numbers use Latin digits, and owners type Latin digits. **[Choice] Latin digits everywhere**, reversible in the formatter.
- A shop has one currency (spec P7). A screen never mixes currencies.
- **Rounding** happens on the server (spec §16: weight totals rounded to whole riel or cents). The app never rounds money for storage.

### Weight (spec T13)

- Stored as grams; shown as kg with up to 2 decimals (`2.5 kg`, not `2.50 kg`). Typed as kg (`inputmode="decimal"`) and converted to grams in the form mapping ([forms §1](./forms.md#1-where-the-forms-pieces-live)).

### Dates and times (spec T14)

- Stored in UTC; **shown in `Asia/Phnom_Penh`** (the `shopTimeZone` runtime value), whatever the device's zone.
- Checked output: `km` → `16 វិច្ឆិកា 2026, 3:40 PM`; `en` (`en-GB` style) → `16 Nov 2026, 15:40`. The formatter picks one style per locale; no screen formats a date by hand.
- Relative times ("2 hours ago", "ready 3 days") use `Intl.RelativeTimeFormat` through the same formatters.

### Phone numbers

- Stored as E.164 (`+85512345678`), normalized on the server (spec §6). Shown in Cambodian national format (`012 345 678`). Formatting uses `libphonenumber-js` (M2.2).

## 5. Data in two languages

Shop data that customers or owners read in either language is stored as two columns: `*_km` and `*_en` (service types, price items, policy text, order line snapshots).

- **Required:** `*_en` is required; `*_km` is optional ([D4](../decisions.md#d4-english-is-the-default-language)).
- **Display:** the active locale's field; if it's empty, the English one. Never show an empty name.
- **Order lines keep both snapshots** (spec §6), so an old order reads correctly in either language after the price list changes.
- **Updates keep the other language:** editing the Khmer name never clears the English one. Forms show both fields; PATCH sends only what changed.
- Search over names matches either language.
