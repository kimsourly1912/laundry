# Server architecture

← [Docs](../README.md) · Queries: [repositories.md](./repositories.md) · Access: [security.md](./security.md) · Tables: [data-model.md](./data-model.md)

Layers, routes, conventions, how data is written, errors, validation, side effects and tests. Helpers named here are built in M1.3 unless marked otherwise; each gets a `reference/` page in the same PR.

---

## Shape of the system

One Nuxt 4 app, deployed as one Cloudflare Worker:

```text
Phone / laptop ──► Nuxt app (SPA screens; /t/** server-rendered)
                     │ same origin, one session cookie
                     ▼
                  Nitro /api ──► Better Auth (/api/auth/**)
                     │
                     ├──► features ──► D1 (NuxtHub db, Drizzle)
                     └──► Telegram Bot API (after the write commits, via the outbox)
Telegram ──► POST /api/webhooks/telegram
Cron ──► Nitro scheduled tasks (outbox delivery, reminders, cleanup)
```

- **The server owns every rule:** prices, totals, order state, payment state, permissions, tenancy. The client asks; it never decides.
- **Rendering (spec T15):** app screens are a SPA. The public ticket page `/t/**` is server-rendered with `no-store`.
- **No public API for outside clients.** A native app or outside client would need its own decision (spec T16).

## Surfaces and routes

| Surface | Path | Who | Access helper |
|---|---|---|---|
| Auth | `/api/auth/**` | Anyone (Better Auth) | Better Auth; organization/member/invitation/ac endpoints blocked |
| Me | `/api/me` | Signed in | `requireSignedIn` |
| Shop | `/api/shop/**` | The owner (staff in Phase 2) | `requireShopPermission` |
| Platform | `/api/platform/**` | Super admin | `requirePlatformPermission` |
| Public | `/api/public/**` | Anyone with a ticket token | none; rate-limited |
| Webhook | `/api/webhooks/telegram` | Telegram | secret-token header |
| Health | `/api/health` | Anyone | none |

Rules:
- **No shop id or slug in shop paths.** The shop comes from the session (spec T3).
- **Resources are plural kebab-case nouns:** `/api/shop/price-items`. Nest only for ownership, at most two levels (`/orders/:id/payment`).
- **CRUD maps to methods:** `GET` list/read, `POST` create, `PATCH` partial update, `DELETE` archive (only where the spec says so: service types, price items).
- **Business actions are `POST` verbs:** `/orders/:id/start`, `/ready`, `/rework`, `/collect`, `/cancel`. Never change state through `PATCH status`.
- **File layout mirrors the URL:** `server/api/shop/orders/[id]/ready.post.ts`.
- A route test (`server/tests/routes.test.ts`) fails when a `/api/shop` or `/api/platform` route calls no access helper.

## Features

Server code is organized by feature, one business area each:

| Feature | Owns |
|---|---|
| `identity` | Better Auth config, permissions, access decisions, owner accounts, password rules, session lifetimes and revocation |
| `platform` | audit events, idempotency keys, job runs |
| `shops` | shop settings, suspend/resume |
| `pricing` | service types, price items |
| `customers` | customers, phone normalization, anonymize |
| `orders` | orders, lines, events, counters, state machine, payment, today view |
| `tickets` | batches, tickets, binding, public lookup, sheet rendering |
| `notifications` | Telegram links, outbox, bot handlers, delivery, reminders |

```text
server/
  api/                thin routes, path mirrors URL
  features/<f>/       the features above
  utils/              shared glue: access, batch, db, errors, validation, idempotency, ids, log, time, telegram, jobs
  middleware/         00.request-id · 10.origin-check · 20.rate-limit
  tasks/              Nitro scheduled jobs (names in shared/scheduled-tasks.ts)
  db/migrations/      generated by drizzle-kit
  tests/              shared util tests; tests/support: the SQLite harness
  error-handler.ts
shared/contracts/     Valibot request schemas + response types, used by server and app
```

### Inside a feature

| File | Does | Must not |
|---|---|---|
| `index.ts` | Re-exports the service functions and types routes and other features may use | Export the repository, schema or internals |
| `<f>.schema.ts` | Drizzle tables, indexes, checks, FKs for **this feature's** tables. Registered with NuxtHub by the `hub:db:schema:extend` hook in `nuxt.config.ts` | Define another feature's tables |
| `<f>.types.ts` | Domain types: records, results, command inputs (usually inferred from `shared/contracts`) | Expose Drizzle table objects to the app |
| `<f>.repository.ts` | Every query of this feature's tables. **Reads run** and return typed rows. **Writes return statements** (not executed), so the service can batch them. [repositories.md](./repositories.md) | Business rules, business errors, calls to other features, HTTP |
| `<f>.service.ts` | Use cases: load via repositories → apply rules → check state and versions → build one batch (guards, audit, idempotency) → run → map the result | SQL; reading `event`, headers or cookies |
| `<f>.errors.ts` | Error codes and small factories (`orderNotEditable(status)`) | — |
| `<f>.rules.ts` | Pure rules: state machine, totals, rounding | I/O |
| `<f>.mappers.ts` | Record → response shape, when not trivial | Queries |

A big feature splits each layer by aggregate with the same suffixes (`orders/payments.service.ts`). Split when a file passes about 300 lines or mixes two aggregates.

### Rules

1. Dependencies point one way: **route → service → repository → schema**. Types and errors are used by all of them.
2. **Routes:** access helper → validate params, body, query → **one** service call. No SQL, no rules.
3. **Only a feature's repository writes its tables.** Repositories never throw business errors.
4. **Features talk through `index.ts` only.** A write that spans features stays atomic: the owner of the action asks the other feature for its **statements** and runs one batch. Example: `orders.markReady` calls `notifications.enqueueStatements(...)` and puts them in its own batch.
5. **Services and repositories take `db` (and `actor`) as parameters** with explicit imports, no Nitro auto-imports, so tests run against plain SQLite.
6. **Nothing in a feature knows about HTTP,** except by throwing from `*.errors.ts`.
7. **Every file carries its feature name** (`orders.service.ts`).
8. **Functions, not classes.** More than two inputs → one options object, destructured in the body.

## Imports and aliases

| Target | Import |
|---|---|
| Server util or another server directory | `#server/utils/batch` |
| Another feature | `#server/features/customers` (its `index.ts`) |
| Shared contract | `#shared/contracts/orders` |
| Sibling file in the same directory | `./orders.repository` |
| Parent directory | Never `../`: use `#server/` or `#shared/` |

ESLint enforces these. A schema file may import another feature's `*.schema.ts` for a foreign key. `vitest.config.ts` mirrors the aliases for plain-Node tests.

## Anatomy of a route

```ts
// server/api/shop/orders/[id]/ready.post.ts
import { orderActionInput } from '#shared/contracts/orders'
import { orders } from '#server/features/orders'

export default defineEventHandler(async (event) => {
  const actor = await requireShopPermission(event, { order: ['transition'] }) // 1. who, allowed, which shop
  const orderId = readIdParam(event, 'id')                                    // 2. validate params
  const input = await readValidBody(event, orderActionInput)                 //    and body ({ version })
  return orders.markReady({ db: useDb(), actor, orderId, input })            // 3. one service call
})
```

The actor (`{ userId, shopId, statements }`) comes from the session; `shopId` is never read from the request.

## Conventions

| Topic | Rule |
|---|---|
| **Ids** | UUID v7 for our tables, generated in the app. Better Auth tables keep Better Auth's ids. Ids are opaque. |
| **Money** (T12) | Integer minor units + a currency code next to every amount. KHR = riel, USD = cents. Never floats. Rounding only in `orders.rules.ts`. |
| **Weight** (T13) | Integer grams. |
| **Time** (T14) | Stored as UTC; sent as ISO 8601. "Today", reports and reminders use `Asia/Phnom_Penh`, computed on the server. |
| **Names** | Tables `snake_case` plural; columns `snake_case` in SQL, `camelCase` in TypeScript and JSON (`casing: 'snake_case'`). Enum values lower `snake_case` with a `CHECK`. |
| **Booleans** | Named as facts (`verifiedPhone`). Never nullable. |
| **Responses** | The resource itself, no envelope. Nullable fields always present (`null`). Never a raw row: map it, so internal columns can't leak. |
| **Lists** | `?page=1&pageSize=20` (max 100) → `{ items, page, pageSize, total }`. |
| **Filters** | Query params named after fields (`?status=ready&payment=unpaid`), `search` for text. Unknown params rejected. |

## Writing data

### Versions

Every editable record has `version`. An edit sends the version it read; the write applies only if it still matches, else **`409 VERSION_CONFLICT`** and nothing changes (spec T8). The response carries the new version.

### State changes

The order state machine (spec §7) lives in `orders.rules.ts`, pure and unit-tested. A transition:
1. Loads the order (by `shop_id` and id), checks the rule: allowed from the current status? Else **`409 INVALID_STATE`**.
2. Writes a conditional update: `WHERE shop_id = ? AND id = ? AND version = ? AND status = ?`, then a guard that exactly one row changed.
3. Adds the order event, audit, and any outbox rows **in the same batch**.

### Lifecycle (never delete)

| Record | Instead of deleting |
|---|---|
| Shop | Suspended |
| Owner user | Banned / password reset |
| Customer | Anonymized: name and phone cleared, Telegram links revoked; orders kept |
| Service type, price item | Archived; order lines keep their snapshot |
| Order | Cancelled |
| Ticket | Voided if lost before binding |

Only `notifications` (sent/skipped after 90 days) and `idempotency_keys` (after 24 h) are purged, by scheduled jobs.

### Atomic writes

D1 has no interactive transactions (spec T9). A write touching several rows is **one `db.batch([...])`**, all-or-nothing:
- Reads for validation happen before the batch. A **guard** in the batch catches anything that changed in between and aborts the whole batch (`requireOneChange` after a conditional update; `requireCount` for set checks). `runBatch(db, statements, onStale)` turns a guard failure into the feature's conflict error.
- **Values the database computes** are computed in the same batch: the order number is `order_counters.last_number + 1`, updated and used in one batch, so two orders at the same moment never share a number.
- **D1 limits:** at most 100 bound parameters per statement (split long lists into chunks, one statement per chunk in the same batch); `LIKE` patterns limited to 50 bytes (search with `instr`, not `like`). The SQLite test harness enforces the same limits. Details: [repositories → D1 limits](./repositories.md#d1-limits).

### Idempotency

Order create and payment record take an **`Idempotency-Key` header** (a UUID the client makes per user action, spec T10):
- First call: the key, a hash of the request and the response are stored **in the same batch** as the action.
- Same key, same request: the stored response is returned (200, same body). The work doesn't run again.
- Same key, different request: **`422 IDEMPOTENCY_MISMATCH`**.
- Two identical requests at once: the second batch fails on the key's unique index, changes nothing, and replays the first.
- A key is scoped to its shop, actor and action. Keys are purged after 24 hours.
- The response must be computable before the batch runs: generate ids up front.

Internal effects use a deterministic key with a unique index instead (the outbox `dedupe_key`: `ready:{orderId}:{version}`, `reminder:{orderId}:{day}`).

### Audit

Every privileged write adds an `audit_events` row **in the same batch**: actor, action (`order.cancel`, `shop.suspend`), target, shop (null for platform actions), safe metadata (which fields changed, never secrets or personal data).

## Errors

Response shape (spec §9): HTTP status = the kind, `code` = the reason.

```json
HTTP 409
{ "code": "VERSION_CONFLICT", "message": "This order was changed on another device. Reload and try again." }
```

- With field problems: `"fieldErrors": { "lines.0.quantity": ["Must be more than 0"] }`.
- Thrown with an `apiError(status, code, message, { fieldErrors })` factory from the feature's `*.errors.ts` (shared codes in `server/utils/errors.ts`). How the flat shape is produced with Nitro's error handler is settled in M1.3.
- **4xx messages are for the user** and shown as they are. **5xx never carry details:** the handler replaces the message and logs the cause with the request id.
- Codes are `UPPER_SNAKE`.

| Status | When | Shared codes |
|---|---|---|
| 400 | Invalid input | `VALIDATION_FAILED` |
| 401 | No session (or expired, revoked) | `UNAUTHENTICATED` |
| 403 | Signed in, not allowed | `FORBIDDEN`, `PASSWORD_CHANGE_REQUIRED`, `NO_SHOP`, `SHOP_SUSPENDED` |
| 404 | Not found, **or another shop's** | `NOT_FOUND` |
| 409 | Stale version, wrong state, already used | `VERSION_CONFLICT`, `INVALID_STATE`, feature codes (`TICKET_ALREADY_BOUND`, `PHONE_TAKEN`) |
| 422 | Refused by a business rule | `IDEMPOTENCY_MISMATCH`, feature codes |
| 429 | Rate limited | `RATE_LIMITED` |
| 5xx | Our fault | `INTERNAL` |

## Validation

- Every input is validated with **Valibot** before any logic: params, query and body. Schemas the app also uses live in `shared/contracts/<domain>.ts`.
- Objects are **strict** on writes (unknown keys rejected). Strings trimmed and length-bounded; numbers and arrays bounded. JSON bodies have a byte limit.
- Validation checks shape. **Business rules live in the service and `*.rules.ts`** ("this price item belongs to this shop and is active").

## Side effects

Anything outside the database (Telegram) happens **after** the batch commits, never inside it (spec T11):
- The action writes **outbox rows** (`notifications`) in its own batch, one per Telegram link, with a unique `dedupe_key`.
- Right after the commit, the route asks to deliver this order's rows with `waitUntil`, so the message goes at once without delaying the response.
- The `notifications:deliver` job (every minute) retries due rows with backoff; after 5 attempts a row is `failed`.
- A `403` from Telegram (the customer blocked the bot) marks the row `skipped` and revokes the link.
- **Order actions never fail because of Telegram** (spec §16).
- Delivery is at least once: a send can repeat if a run dies mid-send. Rows are claimed with a conditional update before sending.

## Tests

| Level | What | Where |
|---|---|---|
| Rules | Pure functions: state machine, totals, rounding | `server/features/<f>/tests/*.rules.test.ts` |
| Services | Every command and query against SQLite built from the real migrations, FKs on: happy path, each error code, **a stale-version case for every conditional write**, **a replay case for every idempotent action** | `server/features/<f>/tests/*.service.test.ts` |
| Tenant isolation | Two shops seeded; shop A can't read or change shop B, for every table and query | `server/features/<f>/tests/*.tenants.test.ts` |
| Routes | Every `/api/shop` and `/api/platform` route calls an access helper | `server/tests/routes.test.ts` |
| Shared utils | Errors, validation, batch guards, ids, log | `server/tests/*.test.ts` |

**Guard rule:** every guard (permission, version, idempotency, tenant filter, state rule) is checked by removing it and seeing a test fail.
