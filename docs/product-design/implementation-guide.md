# Laundry · Repository audit and mockup implementation guide

18 November 2026 · Audited main at [fc5faec](https://github.com/kimsourly1912/laundry/commit/fc5faec5dcda975dfed18059180e7c3c05d53068). Compare against [Laundry Product Notes](./product-plan.md), version 4.

**Decision for these mockups.** Use the agreed mobile counter experience as the product target. Build on the working artwork-and-fields Studio and shared renderer. Treat the HTML editor, AI import, owner order flows, physical printing, item pricing and ready notifications as additions. The images illustrate target behavior. This guide supplies the rules when a generated label or control is ambiguous. Existing repository decisions that need revision are called out below.

## Interaction and visual contract

Reference width is 390 CSS pixels. Verify at 360, 390 and 768, and center at 768 on larger displays. Keep 16px mobile side gutters, readable labels, approximately 44px touch areas and safe-area space below bottom actions. Keep the primary intake action reachable with the keyboard open. Use Nuxt UI tokens and the existing light/dark theme. The reference sheets depict light mode.

Use Overview, Orders, Pickup and More as the compact bottom destinations. Put a named Paper slips entry first in More and a template selector directly in New order. This preserves easy access on a narrow phone. On Overview, count orders received today separately from current outstanding work; use explicit time windows in queries and labels. Unpaid is a payment state. Pair it with a work state wherever the row shows both. Counts may overlap. Use Received, In progress, Ready, Collected and Cancelled in UI. Persist picked_up for Collected if retaining the existing code.

The consistent example is Linda Laundry, Dara, #002139, 2 shirts at ៛2,000 and 1 pair of pants at ៛3,000, total ៛7,000, unpaid. Display dates in the shop timezone. Use the shop currency formatter and approved Khmer strings. Example dates, phone numbers, icons, sample counts and digits in the boards are illustrative. Use one published template for every appearance of the same order. Omit decorative header actions without an implemented purpose.

### Delivery order and acceptance

1. Keep existing tests green. Update decision records for the new cap, Studio modes, ready lifecycle, itemization, Telegram scope and correction rules. Migrate with old-version fixtures. Map existing open orders to Received unless reliable evidence of work state exists. Preserve collected/cancelled and historical manual amounts.
2. Deliver the owner's shortest complete loop first: attached template → fill → preview → save → issue bag number → print or show QR → reopen the order. Two-shop isolation, duplicate submission and reprint are acceptance cases. A browser may know only that the print dialog opened; always provide Print again.
3. Add paid/unpaid handoff, ready/rework and outbox-backed notifications. Keep order changes and queued messages atomic. Confirm bot ownership and customer claim behavior with the pilot shop. Handle late links and a blocked bot.
4. Add structured catalog bindings, line items, customers and prices for the target presets. Before enabling automatic totals on a shop template, map each relevant field to a stable service/item key and unit. Preserve snapshot amounts on every reprint.
5. Add the phone Studio and AI contract as a bounded import experiment. Compile the supported markup into a versioned renderable design with dynamic slots for fields and QR. Keep source for editing and report unsupported classes. Approve Satori only if needed after comparing the Linda and denser City layouts for Khmer, QR and physical print size. Use the same renderer for screen, Telegram and print.
6. Pilot on a real phone and the intended printer. Count boxes and Khmer glyphs must be legible, long labels must fit, a printed QR must claim the correct order and a failed print must never allocate a second pickup number.

## Final image selection and exact implementation details

Use sheets 01–11. Choose the images titled **05 Revised**, **06 Revised**, **07 Revised** and **11 Revised** for those numbers. Match the common Nuxt UI tokens across the set. Use the white app shell from Sheet 01 as the baseline, with one primary action per step.

- **01–04.** Generate numbers and dates from the saved order. Both work and payment have independent text badges. Exact order-number lookup yields at most one match per shop; multiple matches make sense for phone lookup. Use a shared published slip across confirmation, Telegram, order detail and print. Retry appears only for a failed delivery. Before issue, use draft placeholders. Cancel and copy is one explicit correction action.
- **05–07.** The owner views a template with sample fields and fills actual data in New order. The Paper slips destination under More highlights More. The owner sees Telegram connection status; platform administration owns bot connection. The request queue is its own link, outside the template rows. Include suspension/resumption and archive/restore in overflow menus.
- **08–09.** The artwork and HTML panels depict different authoring modes. Use one Publish action per viewport. Keep field placement coordinates in design pixels, convert physical paper dimensions separately. Import version is integer 1, reviewNotes is an array, and placeholders belong inside html as specified in Product Notes. Use only fields in the versioned catalog. Platform screens use platform navigation. The 150 × 90 mm size is sample data.
- **10–11.** Read password limits from shared/contracts/identity.ts (currently 6–128). Retry save with the same submission key. After commit, Print again reuses the order. Show no-template state in template selection and protect existing order/pickup actions. The sample QR, glyphs, colors, handwritten values and dates in generated artwork are illustrative. Use generated-at-runtime QR and shop-approved artwork.
